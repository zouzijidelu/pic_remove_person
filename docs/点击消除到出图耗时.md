# 从点击「开始消除」到图片展示：耗时与资源

| 项目 | 内容 |
|------|------|
| 日期 | 2026-08-20 |
| 机器 | 129 L20，全景约 6720×3360 |
| 目的 | 界面体感远长于 GPU 推理；后续优化、选型对照都看这条链路，不只看 `gpu_infer` |

**结论：** 日志里的 3～7 秒只是服务端 `inpaint`。点消除到右侧出图，还要过 Mask、存盘、Gradio 回传大 JPEG、浏览器解码。LaMa 推理可以比 PowerPaint 快一倍，**界面仍可能差不多慢**，因为后半段两边一样重。

---

## 1. 整条链路（按发生顺序）

进度条在 **45%** 会停住：那一档覆盖整个 `backend.inpaint()`（含贴回），不是「推理做到 45%」。

| 阶段 | 发生在哪 | 进度 | 6720 上大概做什么 | 优化前量级 | 优化后（129，2026-08-20） |
|------|----------|------|-------------------|------------|---------------------------|
| 0. 请求进门 | 浏览器 → Gradio | 无 | 回传原图路径、笔刷层、session | 笔刷若开着，图层很大 | 原图已是 filepath；点选不回传画板 |
| 1. `read` | `remove_person` | 5% | 打开原图到 PIL | 0.1～0.5s | 记入 `[profile]` |
| 2. `mask` | 同上 | 15% | 笔刷/SAM Mask 拉到原尺寸、膨胀 | 0.2～1s+ | 记入 `[profile]` |
| 3. `inpaint` | 后端 | **45% 停在这** | 见下表拆分 | 曾 30s+（整图贴回） | LaMa ~3.4s / PP ~6.9s |
| 4. `save` | 写 `output/*.jpg` | 85% | quality=95 的 6720 JPEG | 0.3～2s | ~0.3s |
| 5. `preview` | Mask 缩略图 | 95% | 最长边 960 | <0.1s | 记入 `[profile]` |
| 6. **handler 结束之后** | Gradio + 浏览器 | 已 100% | 把结果图发给页面并解码 | **常比推理还长** | 改为直接送已保存的 JPEG，不再把 6720 PIL 再编码一遍 |

`handler=` 只统计 1～5。第 0 步和第 6 步不在 Python 函数里，所以**界面秒数 > handler** 是正常的。

### 3. `inpaint` 再拆

**LaMa**（整图降到 `max_side`，默认 2048）：

| 子步骤 | 日志 | 129 实测 |
|--------|------|----------|
| GPU 推理 | `[lama] gpu_infer` | 2.6s（2048×1024） |
| 贴回原图 | `[lama] paste_back` | 0.3s（只贴 Mask 附近；以前整图 LANCZOS 十几秒） |
| 合计 | `[profile] ... inpaint=` | 3.4s |

**PowerPaint / Qwen**（只跑 ROI）：

| 子步骤 | 日志 | 129 实测（PowerPaint） |
|--------|------|------------------------|
| 裁 ROI | `crop=` | 应 <0.5s |
| 拉起 worker | `ensure_worker=` | 已常驻则 ~0；首次含下权重 | 
| 磁盘 ROI + 推理 | `worker=` | 约 6.9s 里的大头 |
| 贴回 | `paste_roi=` | 应 <0.5s |

## 2. 为什么感觉 LaMa 不比 PowerPaint 快

129 同图实测（贴回优化后、handler 内）：

| 模型 | GPU / worker | handler 内合计 | 界面仍可能 |
|------|----------------|----------------|------------|
| LaMa 2048 | gpu_infer 2.6s | ~4s | 再加 Gradio 发图 + 浏览器 |
| PowerPaint 768 | inpaint 6.9s | ~7s+ | 同一套发图 |

差额只有两三秒，人眼不容易觉得「LaMa 快很多」。两边都要存、传一张约数 MB 的 6720 JPEG。

选型不要只比界面秒表，要看：`[profile]` 的 `inpaint=`、显存 `smi=` / `procs=`、以及效果（见对比报告）。

---

## 3. 日志怎么读

每次点消除会打一行：

```
[profile] LaMa read=0.12s mask=0.40s inpaint=3.40s save=0.28s preview=0.05s handler=4.25s | jpeg=2.4MB 6728x3360 | rss=... torch_alloc=... peak=... reserved=...MB smi=12345/46068MB util=8% procs=python:pid=1800MB,python:pid=4100MB
```

| 字段 | 含义 |
|------|------|
| `read` / `mask` / `inpaint` / `save` / `preview` / `handler` | 服务端各段墙钟 |
| `jpeg=` | 结果文件大小 |
| `rss` | Demo 进程 CPU 内存（含 SAM+LaMa） |
| `torch_alloc` / `peak` / `reserved` | **本进程** CUDA（LaMa/SAM）；不含 PowerPaint worker |
| `smi=` | 整卡占用（所有进程之和） |
| `util=` | GPU 利用率，打日志那一瞬，推理刚结束往往已经掉下来 |
| `procs=` | 各进程显存。Demo 与 PowerPaint/Qwen worker 会各占一条 |

LaMa 细项：`[lama] gpu_infer`、`[lama] paste_back`  
PowerPaint：`[powerpaint] crop=` `ensure_worker=` `worker=` `paste_roi=`  
Qwen：`[qwen-edit]` 同样字段

```bash
journalctl -u pano-lama --since "10 min ago" --no-pager | grep -E 'profile|lama]|powerpaint|qwen-edit'
```

界面状态栏也会带 `handler=` 摘要。

## 4. 后续优化优先级（按「点击到出图」）

1. **Gradio 回传 6720 JPEG**（handler 之后，两边模型一样慢）— 结果区改预览 960、原图只提供下载。  
2. **请求进门**：笔刷层不要每轮回传；能关掉就关。  
3. **Mask 拉到 6720**（`mask=`）— 膨胀可在预览尺度做再上采样。  
4. **PowerPaint `worker=`** — 步数 / ROI 边长；与 LaMa 比效果，不单比秒数。  
5. **LaMa `gpu_infer`** — 已是数秒；`max_side` 1024 vs 2048 对墙钟影响小于贴回/发图。  
6. **显存** — 对比时看 `smi` 与 `procs`：PowerPaint 常驻时 LaMa 也会「看起来」更占卡。测 LaMa 独占把 PowerPaint worker 卸掉再看 `procs`。

不要再把整图 LANCZOS 贴回当成优先项，129 上 `paste_back` 已是 0.3s。

---

## 5. 实测摘录（129，2026-08-20）

贴回改成只贴 Mask 附近之后：

- LaMa `max_side=2048`：`gpu_infer` 2.6s，`paste_back` 0.3s，`save` 0.3s，inpaint 合计 3.4s  
- PowerPaint `max_side=768`：inpaint 6.9s  

更早：整图贴回时 LaMa 墙钟 30s+，且 1024 与 2048 几乎一样慢——瓶颈在贴回不在推理分辨率。
